# APBD Real-Time Alerts (P2)
[![CI](https://github.com/faishalnuruz/apbd-realtime-alerts/actions/workflows/ci.yml/badge.svg)](https://github.com/faishalnuruz/apbd-realtime-alerts/actions/workflows/ci.yml) [![License: MIT](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)

Project 2 of the BPKD portfolio PRD, built for real: a SIMDA-shaped MySQL entry by a bendahara
travels through its binary log into Debezium, over Kafka, into a consumer that masks PII, keeps
realisasi-vs-pagu per SKPD, and fires the >90% alert — with the end-to-end latency **measured,
not asserted**: p95 **2.483 ms** against the PRD's 30-second target (`docs/generated/latency-report.md`,
regenerated by every benchmark run, failing the command if the SLA ever breaks).

Where `sikt-mini-lakehouse` answers *"is the data trustworthy?"*, this repo answers *"how fast does
the system notice?"* — both read the same SIMDA-shaped source, so their evidence is comparable.

## What actually runs

| Layer | Component | Real mechanism |
| --- | --- | --- |
| Source | SIMDA-shaped MySQL 8.4 | binary log in ROW format, `binlog_row_metadata=FULL`, dedicated read-only `debezium` account |
| Capture | Debezium MySQL connector | `snapshot.mode=initial` — the initial load and the live stream are the same path |
| Transport | Kafka 3.8 (single-node KRaft) | topics `apbd.siktm.bku`, `apbd.siktm.pagu_anggaran`, manual commits from a consumer group |
| Processing | Python consumer | mask PII → apply CDC semantics (upsert/delete/dedup) → evaluate the 90% threshold |
| Alert | Slack Block Kit payload | edge-triggered on the *set* of breaching SKPDs; dry-run to disk, posts only with a webhook |

Ports are deliberately disjoint from the sikt stack: MySQL **3307**, Kafka **9092**, Connect REST **8080**.

## Quickstart

```bash
docker compose up -d                                  # MySQL + Kafka + Debezium Connect

python -m apbd_stream.seed                            # 5 SKPD, pagu, treasurers, 310 BKU rows
python -m apbd_stream.connector                       # register Debezium, wait until RUNNING
python -m apbd_stream.consume --once                  # drain the snapshot through the pipeline

python -m apbd_stream.benchmark --events 200 --pace-ms 50
```

The benchmark paces 200 real inserts into MySQL (the last one is sized to push a SKPD across the
90% line), drains every batch live, and writes the report. On the machine this repo was built on:

| Metric | Value |
| --- | --- |
| p50 | 1.492 ms |
| p90 | 2.343 ms |
| **p95** | **2.483 ms** |
| p99 | 2.492 ms |
| max | 3.165 ms |
| alert decision on the crossing event | 1.490 ms |
| SLA (PRD: < 30 detik) | 30.000 ms → **PASS** |

**The definition matters more than the digits.** The clock starts at `source.ts_ms` — the commit
timestamp *MySQL itself* wrote for the transaction, carried through Debezium — and stops when the
consumer has masked the event, updated the aggregate, and evaluated the threshold. Same machine,
same clock: no skew correction. It includes binlog read, Connect polling, the broker fetch,
masking, aggregation, evaluation. It excludes Slack delivery and the PRD's production hops
(Pub/Sub, Dataflow), which are documented as designed — see [Honest limits](#honest-limits).

## The alert

The crossing event lands mid-benchmark, and the alert follows within the same measurement. This is
the payload of the run recorded in this repo (`docs/generated/rt_alert_payload.json`) — Dinas Sosial
was already over the line from the seed, and the benchmark's last row pushed Dinas Pendidikan across:

```
*SIKT APBD — 2 SKPD melewati 90% pagu*
*1.05.05* Dinas Sosial      Realisasi Rp 855.60 M dari pagu Rp 900.63 M — sisa Rp 45.03 M (95.00%)
*1.03.03* Dinas Pendidikan  Realisasi Rp 827.55 M dari pagu Rp 900.00 M — sisa Rp 72.45 M (91.95%)
```

- **Edge-triggered**: it fires when the *set* of breaching SKPDs changes (a new breach, a
  recovery), not once per event.
- **Revision-aware**: pagu updates travel the same connector, so a mid-stream budget revision
  changes the verdict without a restart (`test_a_mid_stream_pagu_revision_changes_the_alert`).
- **Dry-run by default**: `docs/generated/rt_alert_payload.json` is always written; the webhook
  POST happens only when `SLACK_WEBHOOK_URL` is set, so no demo can message a real channel.

## PII never leaves the consumer raw

Debezium streams the source truthfully — the raw topic contains raw NIK, and that is correct:
masking belongs to the processing step, not the CDC layer. The consumer runs every envelope
through `mask_envelope()` *before* aggregation, so downstream there is nothing to leak:

```json
{"id_bku": 505, "kode_skpd": "1.01.01", "jumlah": "225000000.00", "tanggal": "2026-10-28",
 "nik_bendahara_hash": "a03ce1863a166a74…", "nik_bendahara_masked": "3275********3321",
 "rekening_tujuan_hash": "1e8e862fba8411d8…", "rekening_tujuan_masked": "0037********5659"}
```

`test_no_raw_pii_reaches_any_downstream` proves both directions: the topic *does* carry the raw
NIK, and none of this repo's artifacts (state, alert payload, evidence files) do.

## CDC semantics, not changelog arithmetic

- **Upsert, not sum** — an UPDATE to a BKU row *replaces* the amount already counted; a DELETE
  withdraws it. Summing a changelog triples budgets; this has its own test.
- **Replay-safe** — at-least-once delivery plus a `topic:partition:offset` dedup key: re-draining
  or restarting cannot double-count.
- **Rebuildable** — the state file is disposable; delete it and the consumer re-derives the same
  aggregate from the topics.

## Honest limits

| PRD element | Status |
| --- | --- |
| MySQL binlog → Debezium → Kafka | built, running, tested (snapshot: 310 BKU + 5 pagu records) |
| PII masking in the stream | built, tested in both directions |
| >90% pagu alert | built (dry-run payload; Slack only with webhook configured) |
| Latency < 30 detik | **measured** — p95 2.483 ms, see `docs/generated/latency-report.md` |
| Pub/Sub, Dataflow, BigQuery | designed only — local analogues: Kafka topics, the Python consumer, the in-repo aggregate |
| Exactly-once delivery | at-least-once + tested dedup, not Kafka transactions |
| HA (multi-broker) | single-node KRaft, by design |

Full per-requirement mapping: [`docs/prd-mapping.md`](docs/prd-mapping.md). Architecture detail,
including why Kafka here and not in P1: [`docs/architecture.md`](docs/architecture.md).

## Tests

```bash
python -m pytest -m "not integration"   # 26 unit tests — masking, CDC semantics, alert, latency math; what CI runs
python -m pytest -m integration          # 7 integration tests — against the real stack (~30 s)
```

The integration suite owns its setup (fresh consumer group and state file per run, connector
registered by the fixture, breach state pinned so assertions don't depend on run history), so it
verifies what a reviewer's first run would — not a state the previous run happened to leave
behind. CI runs the unit layer because the compose stack is a local resource; the split is stated
in the workflow itself.
